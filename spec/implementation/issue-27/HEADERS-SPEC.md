# Issue 27 Follow-up: MCP HTTP Headers and User Token Delegation

**Status**: Approved
**Issue**: [#27 — MCP client configuration](https://github.com/ygo74/ai-enterprise-agent-runtime/issues/27)
**Implementation branch**: `feature/27-mcp-configuration` (current PR #28)

## Goal

Allow an MCP server configuration to define arbitrary HTTP request headers,
including deployment-specific environment values and explicitly selected
identity/request context. Also support OAuth delegation on behalf of the user
when the MCP server requires a downstream token representing that user.

## Configured headers

An HTTP server YAML file may define a `headers` mapping from header names to
string values. Each value may be a literal, an exact `${ENV_NAME}` environment
reference, or a template containing one or more supported `{{TOKEN}}` values.
Environment references use the existing configuration directory and process
environment behavior. Context tokens are substituted for each outbound MCP
JSON-RPC request, so one shared MCP connection can serve concurrent turns.

The proposed context tokens are:

| Token | Value |
| --- | --- |
| `{{USER_ID}}` | `AgentPrincipal.subject`, the authenticated caller identifier used by the runtime |
| `{{USER_EMAIL}}` | `AgentPrincipal.email` |
| `{{USER_NAME}}` | `AgentPrincipal.display_name` |
| `{{USER_ROLES}}` | `AgentPrincipal.roles`, sorted and joined with commas |
| `{{REQUEST_ID}}` | Correlation ID for the current turn, generated by the runtime when absent from the request |
| `{{CONVERSATION_ID}}` | Caller-scoped conversation identifier |
| `{{SESSION_ID}}` | Alias of `CONVERSATION_ID`; this runtime uses the conversation identifier to select the framework session |

Only these explicit values are available. The runtime will not interpolate
arbitrary `AuthenticatedUserContext` claims or forward arbitrary incoming
request headers. `AgentPrincipal` is the identity source because it is the
existing normalized, credential-free contract passed into agent execution.
`UserIdentity`, `AuthenticatedUserContext`, and `ResolvedUser` remain
authentication-boundary models and will not be exposed directly to MCP
configuration.

Environment references must occupy the entire header value. Context tokens may
be combined with literal text. Unknown or malformed tokens fail configuration
validation. If a configured token has no value in the current turn, the request
fails before it is sent rather than silently sending an empty or stale value.

Configured headers apply to HTTP transport only. Configuration values and
resolved headers are treated as sensitive and are redacted from representations
and diagnostics. Header names are compared case-insensitively when checking for
conflicts with API-key, OAuth, or delegated authorization. MCP-controlled
protocol headers remain owned by the MCP transport.

## OAuth on behalf of the user

The existing `authentication_mode: oauth` continues to mean that the MCP client
performs its own authorization-code consent flow and stores its MCP access token.
It is distinct from delegation of the user token used to authenticate to the
agent.

Add a separate `authentication_mode: oauth_on_behalf_of` for HTTP MCP servers.
Its typed configuration names the downstream `audience` and optional `scopes`.
The application supplies a `DelegatedTokenSource` implementation. For each
outbound MCP JSON-RPC request, the runtime provides that source with a typed
request containing:

- the verified `AgentPrincipal`;
- the validated incoming OAuth bearer token as a redacted `AccessToken`, used
  only as the subject token for exchange;
- the configured downstream audience and scopes.

The source exchanges the subject token according to the host's identity
provider, and returns an `AccessToken` intended for the configured MCP audience.
The runtime sends only this returned token as `Authorization: Bearer ...` on the
matching MCP HTTP request. The incoming token is never forwarded to the MCP
server. The source owns provider-specific exchange details and token caching;
the Python runtime does not ship an identity-provider-specific OBO client in
this follow-up.

The incoming credential is retained only in an internal request-scoped context
after successful authentication. It is excluded from serialized auth context,
`ConversationTurn` representations, prompts, logs, and user-facing errors. An
API-key-authenticated, anonymous, or otherwise tokenless request cannot use
`oauth_on_behalf_of` and fails closed. Missing delegated-token source, rejected
exchange, or a returned token whose declared audience does not match the
configured audience also fails closed without sending the MCP request.

The source abstraction may need a typed request shape that includes the
subject-token and scopes; extend the existing `AccessToken` and
`DelegatedTokenSource` contracts rather than introducing a second token model.

## Example

```yaml
transport: http
url: https://mcp.example.test/mcp
capabilities: [mail]
tools:
  find_mail: search
headers:
  Content-Type: application/json
  X-User-ID: '{{USER_ID}}'
  X-User-Email: '{{USER_EMAIL}}'
  X-Conversation-ID: '{{CONVERSATION_ID}}'
  X-Request-ID: '{{REQUEST_ID}}'
  x-api-key: '${ARCHIVE_MCP_API_KEY}'
```

A server using delegated OAuth instead selects `oauth_on_behalf_of` and declares
the audience/scopes for the application-provided token source. In that mode,
`Authorization` is supplied by the runtime and cannot be overridden in
`headers`.

## Acceptance criteria

- The versioned MCP server JSON Schema and runtime loader accept and validate
  the optional HTTP `headers` mapping; stdio configurations reject it.
- Literal values, exact environment references, and documented context tokens
  resolve deterministically without exposing values in `repr`, validation
  errors, or logs.
- Calls through one shared MCP connection send the current turn's identity,
  request, and conversation values. Parallel turns with different callers or
  request IDs do not leak values into one another.
- The `oauth_on_behalf_of` mode requires an HTTP transport, target audience,
  and an injected `DelegatedTokenSource`. It exchanges the validated caller
  token for the configured MCP audience and attaches only the returned token
  to the corresponding outbound request.
- No inbound token is serialized, logged, placed in a prompt, or sent to the MCP
  server. Tokenless callers, missing sources, failed exchanges, wrong-audience
  results, and conflicting explicit `Authorization` headers fail closed.
- Existing authorization-code `oauth`, API-key, proxy, stdio, and direct
  `McpConnection` behavior remains compatible when new modes/headers are
  omitted.
- Documentation and the Python LangChain/FastAPI MCP example demonstrate
  static, environment-backed, context-backed headers and the delegated OAuth
  contract without contacting a remote MCP server or performing live consent.

## Edge cases and security

- Context and delegated tokens are associated with each JSON-RPC request even
  when HTTP sends run in a long-lived SDK task and several calls overlap.
- Optional identity values such as email are required only when their token is
  configured; missing values fail that request.
- A conversation ID is a routing/session identifier scoped by authenticated
  principal, not an authorization claim.
- Static header values can themselves be credentials, so all configured values
  are redacted regardless of source.
- API-key-only auth has no OAuth subject token and cannot silently fall back to
  a shared MCP client token in OBO mode.
- No arbitrary claim lookup, raw auth-context forwarding, or direct subject-token
  pass-through is supported.

## Parity, UX, and performance

This extension remains Python-only because the repository's MCP client and
configuration path are Python-only. It does not add a language-neutral MCP
capability or claim .NET/Java parity. Configuration names, token meanings,
validation, and error behavior are versioned in the Python package schema and
documentation.

Header/context rendering must add no more than 1 ms p95 per outbound MCP HTTP
request on the standard local benchmark environment, excluding network latency
and delegated-token exchange. Token exchange performance and caching are owned
by the injected source and must be measured by its host application.

## Test strategy

Add schema and loader contract tests first, followed by fake-transport tests for
environment resolution, context propagation, authentication conflicts, and
parallel turns using one shared connection. Add fake `DelegatedTokenSource`
tests proving the verified subject token is exchanged for the configured
audience, only the returned token is sent, and failures never fall back to the
subject token. Exercise the internal credential boundary to prove the subject
token is absent from serialized context, prompts, representations, logs, and
errors. Run the existing MCP configuration, registry, connection-lifecycle,
public-surface, and performance checks. Extend the example smoke path to load
the documented configuration without a remote server.

## Decisions for approval

The generic `DelegatedTokenSource` is the provider boundary: the host supplies
its identity-provider-specific exchange implementation, while the runtime
validates caller context and sends the resulting audience-specific MCP token.
No Microsoft Entra or other provider-specific OBO client is included unless
requested separately. Additional claims such as tenant ID, groups, arbitrary
metadata, and parent-message IDs remain outside the header-token vocabulary;
they can be added later as named, typed values for a concrete use case.
